# Datasheet: BBO Capstone Query Dataset

Following the "Datasheets for Datasets" framework (Gebru et al.).

---

## Motivation

**Why was this dataset created?** To support a black-box optimisation (BBO) capstone project: finding the input that maximises each of 8 unknown functions, given only the ability to query a point and observe a scalar output. The dataset exists because an optimisation strategy (a Gaussian Process surrogate with UCB acquisition) needs observed (input, output) pairs to learn from, and because the project itself is assessed partly on the reasoning behind how those pairs were chosen, not just the final result.

**Who created it, and for what task?** The course provided an initial set of observations per function; all subsequent data was generated by the author's sequential optimisation process, one new query per function per week, over 10 rounds. The supported task is single-objective, serial, budget-constrained black-box maximisation.

---

## Composition

**What does it contain?** Eight independent sub-datasets, one per function, each consisting of paired input vectors (`X`, every component in `[0,1]`) and scalar outputs (`Y`). Dimensionality and scale vary substantially by function (see table).

| 2 | 2 | 10 | 19 | −0.069 to 0.611 |

**Format:** original data as paired `.npy` arrays per function (`initial_inputs.npy`, `initial_outputs.npy`); weekly query data as Python dictionaries keyed by function ID and week number, consolidated into the project's pipeline scripts.

**Gaps and known issues:**
- **Uneven spatial coverage.** The original data for every function avoids the exact domain corners (no `x_i` ever at exactly 0 or 1 in the provided data). Some corners remain unexplored even after 9 rounds (e.g. Function 1's `[1,1]` corner was only queried in week 8).
- **Function 1 specifically** has only 2 of 19 points near its one confirmed region of interest (a dip at `[0.65, 0.68]`); the remaining 17 points are functionally indistinguishable background near zero.
- **Three accidental exact-duplicate queries** occurred across the project (Functions 4, 5, 6) before an automated detector was built in week 9 to catch this going forward. One of these (Function 6) was informative rather than wasted: the same input returned two different outputs, directly confirming the function has real measurement noise.
- **No systematic repeated measurements.** Outside that one accidental case, noise level is unverified for 7 of the 8 functions — it is inferred indirectly (via log marginal likelihood) rather than measured directly.

## Collection Process

**Original data:** provided by the course as a fixed starting set per function; the exact sampling method used to generate it is not disclosed (a black-box to the student, consistent with the project's framing).

**Weekly query data:** generated by the author's own adaptive pipeline, one query per function per week, over 10 weeks. Each query was chosen based on all previously observed data for that function (initial data plus every prior week's results), using a Gaussian Process posterior and an Upper Confidence Bound score, with the GP's kernel, noise assumption, and length-scale bound selected per function via log marginal likelihood rather than fixed in advance. Two deliberate deviations from the standard pipeline are part of the record: manual, non-model-driven point selection for Function 1 in weeks where the GP was judged untrustworthy, and an alternating GP/RBF-interpolation hybrid strategy for Function 1 from week 7 onward.

**Time frame:** 10 weekly rounds so far, each round's query submitted and its result incorporated before the next round's queries were chosen — i.e. this is sequential, adaptive data, not data collected all at once.

## Preprocessing and Uses

**Transformations applied:** none to the stored raw data itself — original `(x, y)` pairs are kept exactly as observed. For modelling purposes (not altering the stored dataset), a log-transform of `Y` is applied when fitting Function 5, after a leave-one-out calibration check showed the untransformed model was severely miscalibrated, traced to the function's output spanning four orders of magnitude. The same fix was explicitly tested and rejected for three other functions where no calibration problem existed. A separate transform tested for Function 1 was found to invert the correct ranking of outcomes near zero and was rejected despite an initially promising result.

**Intended uses:** fitting Gaussian Process (or comparable) surrogate models to guide sequential black-box optimisation within this specific project

**Inappropriate uses:**
- **Generalising about the "true" underlying functions.** Several functions (especially 1 and 2, at ~19 points in 2D) are too sparsely sampled to support claims about their true global structure.
- **Treating the data as independent** Because queries were chosen adaptively based on prior results, later points are not independent of earlier ones — standard assumptions behind some statistical tests (e.g. naive train/test splitting) do not hold cleanly here.
- **Benchmarking BO algorithms directly against this data.** It reflects one specific, path-dependent sequence of choices (including manual overrides), not a fixed, algorithm-agnostic test set.
